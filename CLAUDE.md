# CLAUDE.md — ymca-autobook

Standing context + preferences for this project. **Read at the start of each session** and honor these without re-asking.

## Class preferences and the current schedule (private)
- **Kept in the private repo since 2026-10-14**, not here: read `PREFERENCES.md` in `thomashan1/ymca-private` at the start of each session (`gh api repos/thomashan1/ymca-private/contents/PREFERENCES.md -H "Accept: application/vnd.github.raw"`). It holds the class likes/dislikes and the weekly schedule table that used to be in this file. Update it there whenever the lineup changes.

## Booking model
- **Where things are edited (since 2026-10-14): the YMCA Booker app, not the repo.** The Mac app is the source of truth for the weekly classes, away dates and one-day changes (Skip / Book in its Book tab); it keeps them in `~/Library/Application Support/YBookerMac/` (`classes.json`, `away.json`, `skips.json`, `picks.json`) and syncs them to the iPhone through iCloud. It reads nothing from GitHub. Fully independent of GitHub by default; with the optional backup turned on (Settings → "Advanced mode", collapsed, since 2026-10-20; it had its own Advanced tab 10/15-10/20), after every change it **writes** `classes.yml`, `away.yml` and `swaps.yml` into `ymca-private`, one way, for the GitHub backup (`RepoMirror.swift`): skips become skip-only swaps, queued single bookings become book-only swaps. **Hand edits to those three files get overwritten** the next time the Mac's copy changes. To change the lineup or away dates for the user, edit `classes.json` / `away.json` in place (the app notices within 10 minutes and before every opening) or use the app. On the first launch of this version the Mac read `pauses.yml`/`swaps.yml` once more so nothing was lost (`repoImported`). The Mac's token needs Contents: Read and write on `ymca-private` only.
- `classes.yml` = recurring classes to auto-book. **It lives in the private repo** (`thomashan1/ymca-private`) since 2026-10-14; `main.load_config()` reads it from there whenever `PRIVATE_REPO_TOKEN` is set (every workflow), failing closed. A local copy next to the code is git-ignored and only used without the token (and by `gen_workflow.py` / `setup_cronjob_org.sh`); refresh it with `gh api repos/thomashan1/ymca-private/contents/classes.yml -H "Accept: application/vnd.github.raw" > classes.yml`. Booking opens ~7 days ahead, so each class's cron fires ~1 week before and books that future date.
- Away dates live in the **private** repo `thomashan1/ymca-private` (`away.yml`, top-level key `away:`; it was `pauses.yml` until 2026-10-15, renamed for consistency with the app); supports an optional per-class `except:` list to keep booking specific classes on an away day. The summary calendar greys out away days.
- **One-off swaps** ("that Tuesday, skip Cycle and take BODYCOMBAT instead") live in the same private repo as `swaps.yml` (`src/swaps.py`, applied by `scripts/run_due.py`; template at `swaps.example.yml`). Each entry is a class `date` plus an optional `skip:` key from `classes.yml` and an optional `book:` block naming the replacement by name/start/location_ids — **never an occurrence id**, since ids change weekly and can't be written ahead of time. **The original is never released until the replacement is actually booked**: if the replacement is full, errors, or its window hasn't opened, the recurring class stays on the roster, and once the replacement lands the original is cancelled automatically. A replacement still unbooked after its window opened fails the run and sends a ❌ email. Deliberately has **no cron of its own** — swaps ride `book.yml`'s existing fires, because the purpose-built one-off cron for 2026-08-18 fired 46 min late while `book.yml`'s established crons have never exceeded 19 min across 100 runs (measured before the 2026-08-26 incident below — see there for current reliability). **Don't build another bespoke one-off workflow; add a swap.** A swap retires the moment its class starts (not at end of day) — before that fix, every fire after a swapped class had run reported "no bookable occurrence" and emailed a ❌ for work that had already succeeded (2026-08-18).
- **A swap can't win a popular class.** Swaps ride `book.yml`'s existing fires, which are positioned for the *recurring* classes, so a swap's own window may already have opened by the time anything runs — Thursday's earliest fire is 10:30, half an hour after a 9:00 class's window opens. For anything that fills fast, add it to `classes.yml` (real 45/30/15 lead) rather than reaching for a swap. Measured 2026-08-18: BODYPUMP Tue 9:00 Southwest went from window-open to full in under 5 hours, and the Thu 8/20 sitting was already full 2 days out.
- Full Mon-Fri schedule (both branches, 8:30-15:00, no fee/dance/swim/senior/pickleball) is cached in `schedule_snapshot.json` in the private repo, refreshed daily by `.github/workflows/schedule-snapshot.yml` (`scripts/snapshot_schedule.py`). Read it instead of a live browse when just discussing/recommending classes — it has an `updated_at` timestamp; re-browse live only if it looks stale or a one-off dispatch is needed.
- Manual one-off booking: dispatch `book.yml` with `class_key=<key>`. This path now respects `away.yml` (including `except:`), same as `run_due.py` — fixed 2026-09-14 after cron-job.org's `core-mon`/`vinyasa-yoga-mon`/`lift-hiit-mon` fires booked straight through the 9/21 away day (the `--class` CLI path never had `away_ranges` (then `pause_ranges`) wired into `book()`, an oversight from before cron-job.org existed — `--cancel-paused` (now `--cancel-away`) cleaned up the 3 stray bookings that day). For a genuine override of an away day, use `book_id=<occurrence id>` instead (via `--browse`/`--list` to find it) — that path books a specific occurrence directly, independent of `classes.yml` and away dates, by design.
- `book.yml`'s per-class cron was generated from `classes.yml` by `scripts/gen_workflow.py`; with `EMIT_SCHEDULE = False` (below) it no longer carries any class cron, so a classes change needs no regeneration. `regen-book.yml` was deleted on 2026-10-14 (it watched the public `classes.yml`, which moved). If `EMIT_SCHEDULE` is ever turned back on, run `python scripts/gen_workflow.py` against a fresh local copy of `classes.yml` and commit — GITHUB_TOKEN can't push under `.github/workflows`.
- **Lead times and `OPEN_GUARD` are coupled — move them together.** `gen_workflow.FIRE_LEAD_MINS` is `[45, 30, 15]`; each lead emits a PDT and a PST cron line and **both fire all year**, so the out-of-season twin arrives `lead + 60` min before the open and `main.OPEN_GUARD` (60 min) is the only thing making it exit instead of waiting an extra hour. Every lead must therefore stay **under 60**. The earliest lead is the delay budget: a late run still books on time because it waits for the true instant. Measured over 100 scheduled runs *before* the 2026-08-26 incident, GitHub's queue delay was median 4.3 min / p90 13.4 / max 18.8 — the 45 min lead is ~2.5× the worst seen; treat this as historical, not current, until the incident below is confirmed resolved. A class can widen its own margin without touching everyone else's via an optional per-class `extra_leads: [...]` list in `classes.yml` (same `<60` ceiling) — currently used for `bodypump-tue`/`bodypump-thu` (`[50, 10, 5]`, doubling them to 6 leads). Wed's two classes additionally pilot GitHub's native `timezone:` cron field (GA March 2026) — one line per lead instead of a hand-written PDT/PST pair, since GitHub handles the DST switch itself; `gen_workflow.NATIVE_TIMEZONE_DAYS` controls the rollout scope.
- **Redundant triggers race, and losing is normal.** Every class fires several triggers that all wait for the same open instant, so one books and the rest get the API's `taken`. That was in neither the retryable nor terminal error set, so it burned 3 retries and sent a ❌ for a class that *was* booked — false alarms on 2026-07-22, 07-27, 08-10 and 08-12. `book()` now re-reads the occurrence on `taken`/`already_joined`: booked by us → quiet success (the winner already reported it), booked by someone else → still a real failure. Don't "fix" the race itself; the redundancy is the point.
- **The Mac is the primary booker; GitHub is the backup (since 2026-10-14).** Both still fire for every class, but at the opening second `book()` waits `BACKUP_GRACE_SECONDS` (5 s, env `BOOK_BACKUP_GRACE_S`; 0 = old behavior) past the open, re-reads the occurrence, and books only if it isn't already ours — a quiet success ("the primary booker (the Mac) got it") otherwise. The Mac's join reply lands ~0.7-1.1 s after the open; BODYPUMP, the fastest filler, takes ~34 s, so the backup still has room. Before this, the two raced and split the wins (GitHub 4, Mac 3 over 10/12-10/14). Manual paths (`--book-now`, `--book-id`) don't wait.
- **Pushing `book.yml` can cost that day's scheduled runs.** GitHub re-registers the schedule when the file changes, and on 2026-07-30 a ~10:03 push was followed by both of that morning's booking crons never firing — Cycle Sculpt for 8/6 had to be booked by hand. Avoid regenerating cron on a day a booking window opens, and verify afterwards. (Separate from — and now dwarfed by — the standing incident below.)
- **Ongoing since 2026-08-26: book.yml's scheduled triggers are severely delayed, and it isn't our workflow structure.** GitHub's status history shows a Critical Actions incident that day, 15:02-15:45 UTC — "Actions jobs failed to start," caused by database saturation, with jobs stuck in a queued state until a force-revoke mitigation was deployed. Right around then, this repo's booking cron started degrading: elevated delay (100-170 min, not the usual single digits) on 8/26, then apparent full silence for a day on both 8/27 and 8/28 (BODYPUMP Thu, Cycle Sculpt Thu, CORE Fri, Lift & H.I.I.T. Fri — all booked by hand), while every other, much smaller scheduled workflow in this repo (Bookings snapshot, Bookings ledger) fired normally throughout. Tried and **ruled out** as the cause, in order: (1) splitting the 78-line file into `book-mon.yml`..`book-fri.yml` (max ~24 lines each) — an 18-line brand-new file still went quiet; (2) a same-afternoon throwaway workflow with a trivial imminent cron, created minutes before its own fire time — also no immediate fire, ruling out "stuck state tied to an old file's history" specifically. Repo-level Actions settings are normal (enabled, unrestricted, active). **Reverted back to the single `book.yml` on 2026-08-31** since the split never fixed anything and there's no reason to carry its extra complexity.
- **The real pattern, discovered 2026-08-31: not silent, just delayed by hours.** `book-mon.yml` (before the revert above) sat quiet for ~73h after creation, then fired a 4-run burst 21:42-22:03 UTC that day — **~11 hours** after Monday's actual windows (10:45am-12:20pm PT) had already opened and passed. Same "long delay then backlog burst" shape as 8/26-28, just compressed. A 10-20 minute delay is tolerable (that's what the 45/30/15 leads already buffer against); an 11-hour one makes `schedule:` triggers useless for classes that fill within ~5h of opening. Two throwaway-workflow retests that same evening, checked after 20-70 min, came back empty — consistent with this pattern, **not proof the scheduler is dead**, since an hour isn't long enough to rule out an eventual delayed fire.
- **Every class now has an independent trigger via cron-job.org** (`scripts/setup_cronjob_org.sh`, added 2026-08-31, generalized from BODYPUMP-only to all 11 classes / 13 jobs on 2026-09-01). cron-job.org calls the exact same `workflow_dispatch` endpoint (`.../workflows/book.yml/dispatches` with `class_key`) a manual dispatch would — one fire per class at -15m, two (-30m/-10m) for classes carrying `extra_leads` (BODYPUMP). No new booking logic, just an external clock. Run the setup script locally with `CRONJOB_ORG_API_KEY` and `GITHUB_PAT` (a fine-grained token scoped to just this repo, Actions: Read and write) — neither secret is ever committed or pasted into chat.
- **`swaps.yml` silently stopped being applied on 2026-09-01, fixed 2026-09-21.** Swaps only ever get applied by `run_due.py`, which used to run via GitHub's own blank `schedule:` fires (no inputs -> book.yml's shell falls through to `else: python scripts/run_due.py`). Once those were paused in favor of cron-job.org, nothing invoked that path any more — all 13 cron-job.org jobs dispatch with an explicit `class_key`, hitting the `--class` branch directly, never the blank one. Caught when setting up the 10/2 BODYCOMBAT-for-Lift&H.I.I.T. swap. Fixed with a 14th cron-job.org job, `swap-check` (also created by `setup_cronjob_org.sh`, on an unfiltered run only): a single job firing on a blank dispatch every 30 min, 9:00-13:30 PT, Mon-Fri (one job via cron-job.org's native multi-hour/multi-minute/multi-wday arrays — safe here since every hour shares the same minute set, unlike the per-class jobs where combining hours and minutes would cross-product). **Since 2026-10-06 a blank dispatch is swaps-only:** `run_due.py` processes `swaps.yml` and skips the recurring classes (each has its own cron-job.org trigger), and exits before logging in when no swap is pending (`RUN_DUE_ALL=1` restores the old check-every-class behavior). Before that, every sweep checked every class, which sat waiting on other classes' openings (two Wed sweeps hit the 90-min timeout) and went red whenever Fisikal returned its 503 "heavy load (queue full)" page for a class that wasn't even due — seen right at BODYPUMP's 10:00:00 opening on 10/6. Same change fixed **skip-only swaps** (`skip:` with no `book:`): they used to work only by stopping the sweep's own booking, but the per-class `--class` path doesn't read swaps and booked the original anyway (Cycle Sculpt 10/1 stayed booked despite its skip). `_run_swap` now releases the original once it's on the roster.
- **No browser since 2026-10-07: login is plain HTTP.** Every run used to download ~180 MB of Chrome (`playwright install`) just to fill in egym's login form, which is a plain jQuery form. On 10/7 Playwright 1.63 shipped a new Chrome build; the 10:15 RPM run hung on that download for its whole 90-min timeout and RPM 10/14 went unbooked until it was booked by hand by occurrence id. `src/login.py` now does the SSO over httpx (GET login page → POST credentials → follow the returned `fisikal.com/egym_login?token=…` → read the CSRF meta), and `src/http_context.py` gives httpx Playwright's `context.request.get/post/delete` shape so `fisikal.py` and the booking logic didn't change. Runs are ~16 s end to end instead of ~1 min. Two Fisikal quirks worth knowing: an API call **without** the session cookie returns a Rails **500** (not 401), and the account allows **multiple concurrent sessions** (a new login doesn't evict a run that's mid-wait).
- **GitHub's own `schedule:` triggers are paused as of 2026-09-01** (`gen_workflow.EMIT_SCHEDULE = False`; `book.yml` regenerated with the `schedule:` block omitted entirely — `workflow_dispatch` is untouched, so cron-job.org, the iOS app, and manual runs all still work). `bodypump-watchdog.yml`'s own schedule is commented out the same way. This was originally additive-only design (GH schedule as free backup under cron-job.org) but on 2026-09-01 — cron-job.org's first real day of full coverage — GH's own crons for `bodypump-tue` fired **3-4 hours late** (scheduled 9:10-10:15am PT, actually ran 12:22-12:56pm PT), the same "backlog burst" pattern as 8/26-31, while cron-job.org's dispatches landed on time and booked correctly (verified via `gh run view --log` on both). Pausing rather than deleting: flip `EMIT_SCHEDULE` back to `True` (and uncomment the watchdog's `schedule:` block) and regenerate once GitHub's scheduler has demonstrated reliable timing again over a real stretch of runs — no fixed date, just evidence. Until then cron-job.org is the sole timing source for every class, so if IT has a bad day nothing else is currently catching it.

## iOS app
- **YMCA Booker, one SwiftUI app under `app/` for macOS, iOS and iPadOS** (since 2026-10-14; it was `ios/` plus a separate Mac app on `explore/macos-app`). On the Mac it's the booker (menu bar, books at the opening second, publishes to iCloud); on iPhone and iPad it's the viewer. In GitHub mode the iOS side is a control panel over the GitHub state (Actions books; the app never books directly). Signs in with a fine-grained PAT (Contents + Pull requests + Actions + Workflows) stored in the device Keychain.
- Schedule → Away dates also lists **upcoming one-off swaps** from the private repo's `swaps.yml` (read-only — securing a swap means booking the replacement before releasing the original against a live window, which stays the Actions engine's job).
- Reads `classes.yml`, `away.yml`, `swaps.yml`, and two private-repo snapshots: `schedule_snapshot.json` (class end times/durations) and `bookings.json` (actually-booked classes with room/instructor, published by `scripts/snapshot_bookings.py` via `.github/workflows/bookings-snapshot.yml`, every 6h). The Week view merges the recurring plan with real bookings.
- **Default data source since 2026-10-14: iCloud from the Mac side of the same app.** The bundle is `com.thomashan.ymcaautobook` on every platform. The old Mac app was `com.thomashan.ybooker.mac`; its Keychain service name and Application Support folder are kept on purpose. No token needed, plus booking-result alerts via a CloudKit subscription. Since 2026-10-14 both platforms can **book or cancel any single session** (Mac and iPhone/iPad: Classes → Add a class, or a class in Schedule; since 1.1 the Mac window and the iPhone share three tabs: Schedule, Classes, Settings): the iPhone sends `BookRequest` records through iCloud and the Mac books it now or at its opening second. Skipping a lineup session there reaches GitHub too: the Mac writes it into the private repo's `swaps.yml` as a skip-only swap marked `note: "Skipped in YMCA Booker"` (and removes it on Unskip; it never touches other entries), and `main.py --class` honors skip-only swaps. That needs the Mac's token to have Contents: Read and write; with a read-only token the Mac shows a warning under Settings → Advanced mode (always collapsed at first; its title shows a ⚠ while there is a backup error). GitHub is the advanced option (iPhone: Settings → Advanced → Use GitHub instead). **Independence is enforced, not just conventional (2026-10-15):** iOS `GitHubClient.send` refuses every call unless the data source is GitHub (`allowed`), and a Mac launched with no backup repo marks its one-time repo import done (`RepoSync.settleImport`), so turning the backup on later never replaces the Mac's own away dates. Tests: `IndependenceTests` (iOS), `GitHubBackupTests` + `testSkipReasonFromTheMacsOwnData` (macOS). The README calls the Mac setup **Option A** (user-friendly) and GitHub **Option B** (advanced). See `app/README.md`.
- **Away dates can be added and removed on the iPhone/iPad in iCloud mode (since 2026-10-15):** the phone saves an `AwayRequest` record (add/remove, start, end, note); the Mac applies it to `away.json` (`Engine.applying`), deletes the request and publishes as usual. Until then the phone shows the change already applied. Classes still can't be edited on the phone (#148).
- **Three tabs since 1.1 (2026-10-20), on the Mac and iPhone/iPad alike:** Schedule (two weeks of your classes with status, plus earlier this week on the Mac from its booking log; swipe/click to skip, cancel or stop weekly; Away dates sheet; calendar grid on iPad and Mac), Classes (Every week with fill-speed badges, Just once, **Add a class** = the YMCA schedule with Every week / Just once; fill-speed table one link away; each class there shows how fast it fills (Browse weekly slots was folded in, 10/20)), Settings (incl. Booking history). Before: Week, Classes (Book | Weekly | Fill speed), Upcoming (Openings | Away), Settings. **Weekly classes can be added/removed from the phone (#148)** via `BookRequest` records with action `addWeekly`/`removeWeekly` (no new CloudKit record type, so no schema deploy needed); the Mac applies them in `Engine.applying(_ [WeeklyChange], to:)`.
- Editing classes (delete) opens an auto-merging PR against `classes.yml`; away-date edits write directly to `away.yml` in the private repo. See `app/README.md`.

- **Mon / Wed / Fri ~12:07 AM PT** (early + off-peak to dodge GitHub's cron-queue delay).
- Mon = this week; Wed & Fri = this + next week. Date format M/D. Away days blocked out in the calendar.
- **Standard schedule email — manual only since 2026-10-14** (`scripts/standard_schedule_email.py`, `.github/workflows/standard-schedule-email.yml`, `workflow_dispatch`). ## Notifications
- Native **GitHub iOS push, failures-only**. Don't add per-run success pings unless asked.
- **Email alert on failed booking attempts** (issue #33 — originally wanted text messages, but AT&T shut down its free email-to-SMS gateway for good on 2025-06-17 with no free replacement, so this alerts by email instead): subject prefixed with ❌, sent via the existing `NOTIFY_EMAIL`/`GMAIL_APP_PASSWORD` creds. Fires for real booking attempts only (scheduled auto-booking, manual `--class`, manual `--book-id`) that fail — not successes (the summary emails already show those) and not cancellations. Fail-open: unset means no alert, everything else unaffected.

## Ground rules
- Always start from latest `main` (`git fetch origin main`). Land changes via **PR** (main is protected). **Never force-push.**
- **Keep `main` clean** — no temporary/debug workflows or scratch scripts on `main`; use throwaway branches for those.
- Credentials live only in GitHub Actions secrets (`EGYM_USERNAME`, `EGYM_PASSWORD`, `NOTIFY_EMAIL`, `GMAIL_APP_PASSWORD`, `PRIVATE_REPO_TOKEN`). Never commit secrets. Personal away-dates stay in the private repo only.
